# Decision register

Every binding decision on this project, with its source. This file answers **"what was decided,
and where does it come from"**.

It is deliberately **not** instructions. `CLAUDE.md` holds the operating rules a session follows;
this file holds the decisions those rules rest on. No rule appears in both — if you are looking
for what to *do*, read `CLAUDE.md`; if you are looking for *why*, read here.

Every entry cites a section of a committed document. CI verifies those citations resolve, so a
stale entry fails the build rather than quietly misleading a session.

## Architecture

| # | Decision | Source | Date |
|---|---|---|---|
| D-001 | **Rust for both core and server.** The client core must embed in React Native, native iOS/Android, and WASM; Go has no credible path there. Splitting core (Rust) from server (Go) would forfeit one protocol crate and one simulation harness exercising both in the same seeded run. | Design §3.1 | 24 Aug 2026 |
| D-002 | **The core is sans-IO.** `credsync-core` performs no I/O and never consults the real world. `Clock`, `Entropy`, `Storage`, `Transport` are trait parameters. This is what makes deterministic simulation possible, and is also the beginner-friendliest shape — the core is plain synchronous Rust. | Design §4.1 | 24 Aug 2026 |
| D-003 | **The protocol spec has a four-page ceiling.** If it grows past four pages, scope has crept. The ceiling is a scope alarm, not a formatting preference, and is asserted mechanically in CI. | Design §5 | 24 Aug 2026 |
| D-004 | **Snapshots down, commands up.** State flows down as ordered full-row snapshots from an append-only log; writes flow up as domain commands the host validates. Business data is never merged by guesswork. | Design §1 | 24 Aug 2026 |
| D-005 | **No CRDTs, no peer-to-peer, no partial-field diffs, no realtime transport.** The strongest teams in the field (ElectricSQL, Replicache) walked back automatic merge. A push notification is only ever a hint to run the loop. | Design §2, §5.3 | 24 Aug 2026 |
| D-006 | **Domain logic never lives in `credsyncd`.** Validated commands are forwarded to the host's registered endpoint. This keeps the engine backend-agnostic: any stack that can expose one HTTP endpoint and write two tables can adopt credSync. | Design §4.2 | 24 Aug 2026 |
| D-007 | **Canonical encoding is compact JSON in v1**, with the codec isolated in `credsync-protocol` so a binary encoding (postcard/CBOR) can arrive as protocol v2 without touching the state machine. Debuggability wins while the protocol is young. | Design §5.3 | 24 Aug 2026 |
| D-008 | **Three conflict classes, declared not conventional.** Server-authoritative (pull-only), owner-draft LWW-per-field, and append-only. The entity registry enforces the class; the simulator generates invariants per class, so a policy claim is a tested property. | Design §6 | 24 Aug 2026 |
| D-009 | **Silent loss is a protocol violation, not a tradeoff.** A losing LWW version returns to the device and is stored as a recovered draft. | Design §6 | 24 Aug 2026 |

## Toolchain

| # | Decision | Source | Date |
|---|---|---|---|
| D-021 | **Rust toolchain is pinned to an exact stable version**, currently **1.98.0** (released 2026-08-18), via `rust-toolchain.toml`. MSRV equals the pin and is declared as `rust-version` in every crate. Bumps are deliberate PRs. A floating toolchain could change behaviour mid-project, which is unacceptable for a system whose core promise is that a seed replays identically forever. | Owner choice | 25 Aug 2026 |
| D-022 | **Edition 2024.** | Owner choice | 25 Aug 2026 |
| D-023 | **`#![forbid(unsafe_code)]` in `credsync-core` and `credsync-protocol`.** `unsafe` appears only in generated FFI scaffolding. Loom is unnecessary by design: the core is single-threaded, and concurrency lives at the bindings' edges and in `credsyncd`, which the simulator exercises. | Design §7.2 | 24 Aug 2026 |

| D-024 | **Workspace clippy lints deny `unwrap`, `expect`, `panic`, `todo` and `unimplemented`.** A silent panic in a decoder is a remote crash; a silent unwrap in the core is lost user data. Denied rather than warned so they cannot accumulate. `iter_over_hash_type` is denied too: `HashMap` iteration order is randomised per process, a real nondeterminism source inside a seeded simulator. | This slice (CS-1) | 25 Aug 2026 |
| D-025 | **Release profile sets `lto`, `codegen-units = 1`, `strip` and `panic = "abort"`.** Set at CS-1 rather than CS-25 because the 3 MB-per-ABI size budget is far easier to hold from the start than to claw back once the core is large. | Design §11 | 25 Aug 2026 |

| D-026 | **CodeRabbit reviews every PR, profile `assertive`.** Playbook §5 makes the CI gates the reviewer, but gates only catch what someone thought to encode. `.coderabbit.yaml` carries the non-negotiables as per-path instructions so the review is against this project's rules rather than generic advice. Generated docs are excluded: reviewing them means reviewing Word's output. | This slice (CS-2) | 26 Aug 2026 |
| D-027 | **The four-page ceiling is enforced as ≤190 lines of `docs/spec.md`.** A line count is a crude proxy for pages but it is unambiguous and cannot be gamed by formatting. Verified to actually fail at CS-2 by padding the file — a gate that cannot fail is worse than no gate, because it reads as coverage. | Design §5; This slice (CS-2) | 26 Aug 2026 |

| D-028 | **`snapshot` and `payload` may contain no floating-point numbers, at any depth.** Discovered at CS-3: `serde_json` float parsing is not exact — `2.2283095771495367e-21` re-parses one ULP away and re-encodes shorter — so a document holding a float does not survive a serialize/parse/serialize cycle unchanged. Since scope digests are computed over the canonical encoding, that would let two sides holding the same logical row compute different digests, and the client would re-bootstrap against a divergence that never happened: the detector firing on itself. Hosts use scaled integers or decimal strings, which are exact and portable where JSON floats are not. | This slice (CS-3); Design §5.2 | 26 Aug 2026 |
| D-029 | **Canonical encoding routes through `serde_json::Value` rather than serializing structs directly.** `serde` emits struct fields in declaration order, so a direct encode would make every digest depend on the order fields happen to be written in — someone tidying a struct would silently change every digest in the system. Going through `Value`, whose `Map` is a `BTreeMap`, sorts keys recursively and removes that coupling. The `preserve_order` feature must never be enabled. | This slice (CS-3) | 26 Aug 2026 |
| D-030 | **`CommandId` is parsed by hand rather than via the `uuid` crate.** The crate's v7 generation features depend on `getrandom`, which is on the sans-IO ban list for `credsync-core` — and core depends on `credsync-protocol`, so it would appear in core's dependency graph and fail the CI gate. Hand-parsing also enforces the version-7 nibble, which the crate does not. | This slice (CS-3); D-002 | 26 Aug 2026 |

| D-031 | **O-001 closed: xxh3 for batch checksums and scope digests, BLAKE3 for command payload checksums, both truncated to 128 bits.** Benchmarked at CS-4 across the sizes the spec actually names (256 B to 256 KB): xxh3 runs 4.6x faster on average, 2.2x-6.3x by size. The split follows the threat model rather than a single winner. Checksums and digests ask *is this intact* on a channel TLS already protects, and run per batch and per row on a battery-powered phone. A command checksum asks *is this the body originally sent* - refusing a mutated replay is a promise no non-cryptographic hash can make, and there is one per command rather than one per row, so the cost lands where it is affordable. Design v2.1 §5.1 draws the same line. Re-run `cargo run --release --example hash-benchmark`. | This slice (CS-4); Design §5.1, §12 | 27 Aug 2026 |
| D-032 | **The scope digest sums per-row hashes in wrapping `u128`, rather than XORing them.** Addition is commutative so order cannot matter, and has an exact inverse so a tombstone restores the digest to precisely its prior value. XOR has both properties too, and is the obvious choice, but it is self-inverse: two identical rows cancel, so a bug that duplicated a row would produce the digest of a scope where the row is absent - and the mechanism whose entire purpose is noticing silent divergence would report agreement. Row fields are length-prefixed for the same reason: without that, `("lesson","a1")` and `("lessona","1")` collide. | This slice (CS-4) | 27 Aug 2026 |
| D-033 | **`twox-hash` rather than `xxhash-rust` for xxh3.** `xxhash-rust` is BSL-1.0, outside the allowlist in `deny.toml`; `twox-hash` is MIT. The licence gate chose the crate, which is the gate working as intended (D-011). | This slice (CS-4) | 27 Aug 2026 |

| D-034 | **`digest` and `checksum` are exactly 32 hex characters, not at most 64.** With O-001 closed the width is decided, so any other length is malformed rather than merely unusual. Enforcing a ceiling instead would let a two-character checksum through the decoder while every producer emits 32 — a gap between what the spec declares and what the wire accepts. Found by review at CS-4, in a divergence introduced by CS-4 itself. | This slice (CS-4); D-031 | 27 Aug 2026 |

| D-035 | **Registry publishing is deferred until the engine exists; CS-5 keeps only the fixtures.** The Slice Plan reserved `credsync` and `cred-sync` on crates.io and npm at CS-5 via `0.0.1` placeholders. Owner decision: credSync is consumed locally — path dependencies and `npm link` — inside the Dream Lab OS repos first, and the registries are approached when there is a real release to put on them. A placeholder claimed months ahead of anything to publish is a name held with nothing behind it, and bundling an irreversible outward act into a slice meant CS-5 could not close on its own proof. Name reservation is now issue #43, milestone M7. **The risk accepted:** all five names were re-verified free on 23 Sep 2026, and a name reserved later is a name someone else can take first. | [Slice Plan](build-slice-plan-v1.0.md) §1; owner decision | 23 Sep 2026 |

| D-036 | **Golden fixtures are committed evidence, and no regeneration script ships with them.** A fixture one command away from agreeing with whatever the code now does proves nothing: the failure it exists to cause would be reflexively regenerated away. So a moved fixture is read as a wire change and answered by updating [spec.md](spec.md) and the fixture together. The same reasoning drives the drill — rather than breaking one fixture by hand once, every byte of every fixture is perturbed on every run and must be rejected, so an assertion that has quietly become vacuous fails immediately instead of passing for months. | This slice (CS-5); [Spec](spec.md) §2 | 23 Sep 2026 |

| D-037 | **The engine owns all four traits; `Storage` answers inline, `Transport` answers by event.** Design §4.1 lists *"storage results"* among the events fed to the core, which would put `Storage` on the caller's side alongside `Transport`. Owner decision at CS-6: the engine holds `Clock`, `Entropy`, `Storage` and `Transport` and calls them directly. `Storage::transact` is synchronous and answers immediately, so routing its outcome back through the event queue would mean parking a half-finished apply across a round trip — and `docs/spec.md` §4 requires that rows and cursor commit together, which is precisely the state that must not be interruptible. `Transport` is different in kind: a request handed to a network that routinely does not answer cannot be awaited, so it keeps `Event::TransportResponse`. `Effect` therefore carries only what the traits cannot express — `ScheduleRetry` and `Emit`. This supersedes the reading of Design §4.1 and the worked example in the `rust-sans-io` skill, both corrected in this slice. | [Design](credsync-design-v2.1.md) §4.1; owner decision | 23 Sep 2026 |

| D-038 | **The sans-IO ban list is checked against the source, not only the dependency graph.** CI has greped `cargo tree` since CS-1, which catches `tokio` and `reqwest` and misses the likelier failure entirely: `SystemTime::now()` needs no dependency, changes no manifest, compiles, and leaves every test green while deterministic replay is silently gone. `scripts/check-sans-io.sh` greps the source of `credsync-core` and `credsync-protocol` for the banned constructs, stripping comment-only lines so the prose explaining the ban does not trip it. The two gates are complements. CLAUDE.md §3 opens with *"a rule that cannot be checked is a wish"*; until CS-6 this particular rule was one. | This slice (CS-6); D-002 | 23 Sep 2026 |

| D-039 | **`Storage` gained a `row_version` read at CS-7.** The scope digest is a sum of per-row hashes over `(entity, entity_id, row_version)`, so replacing a row means subtracting its old contribution before adding the new one, and a tombstone means subtracting at *the version actually stored* — neither of which is knowable from the change alone. The alternative was to have each adapter maintain the digest, since it already knows the row it is overwriting; rejected because it would put the subtlest arithmetic in the system into every port, where one wrong tombstone produces phantom divergence on real devices. Keyed by `(entity, entity_id)` with no scope, because the registry maps each entity to exactly one scope, so a scope parameter could only ever disagree with the entity. | This slice (CS-7); [Spec](spec.md) §5; D-032 | 23 Sep 2026 |

| D-040 | **A client cannot detect a missing *middle* change, and is not asked to.** `seq` is a `bigserial` shared by every scope, so one scope's entries are sparse — `1, 2, 7, 19` is healthy. There is no contiguity to check, and an apply path demanding it would reject almost every real batch. What the client does enforce is that the server never sends it backwards: strictly increasing `seq`, nothing at or below the cursor, and a `next_cursor` that covers what was sent. **The scope digest catches the rest**, which is the clearest statement of why it exists: a change dropped in the middle leaves the client holding rows the server does not have, the digests disagree, and the scope re-bootstraps. Ordering arithmetic and the digest cover different halves of one problem. | This slice (CS-7); [Spec](spec.md) §4, §5 | 23 Sep 2026 |

| D-041 | **Staging a batch must read its own writes.** Digest maintenance reads each row's current version, but a batch commits as one transaction, so a change staged earlier in the same batch has not committed and is invisible to `Storage::row_version`. A row created and deleted inside one batch — routine, since a pull window spans days for an offline device — was therefore added to the digest and never subtracted. The client would disagree with the server on every later pull and re-bootstrap forever: the divergence detector firing on damage it caused itself. The apply path now carries an in-batch overlay of pending row versions that takes precedence over storage. **Found by the property test at CS-7 on a two-change sequence, not by review** — which is the argument for `proptest` over examples, made concretely. | This slice (CS-7); D-039 | 23 Sep 2026 |

| D-042 | **A fifth trait, `Compressor`, rather than a compression dependency in the core.** `docs/spec.md` §2 makes byte budgets **compressed-size** budgets and negotiates Brotli or gzip on the wire, so the core cannot know which algorithm the transport will use. Compressing inside `credsync-core` would add a dependency to the one crate whose dependency graph is a guarded non-negotiable, and would still only produce a guess that could drift from the bytes actually sent. The caller instead supplies the compressor its transport really uses, so the number the engine budgets against is the number that goes on the wire; the simulator supplies a deterministic fake, as for the other four. Implementations must be pure — a compressor with adaptive state would make batch composition differ between two runs of one seed. | This slice (CS-8); [Spec](spec.md) §2; D-002 | 23 Sep 2026 |

| D-043 | **`superseded` is a third terminal outcome, not folded into `applied`.** CS-8's slice text listed three statuses while its definition of done named only two exits from the outbox. A superseded command was resolved server-side by a later command overtaking it — a real resolution, not a failure — but a UI showing "saved" for a superseded draft tells the user something false, and telemetry that cannot separate the two cannot notice a server superseding far more than it should. Issue #9's definition of done was corrected before implementation rather than after. | This slice (CS-8); [Spec](spec.md) §3.3 | 23 Sep 2026 |

| D-044 | **An outbox entry can only leave through `StorageOp::ResolveCommand`.** There is deliberately no op that deletes an entry. Removing the entry and recording its [`Resolution`] are one operation and one transaction, so "never silently dropped" (`docs/spec.md` §3.3) is enforced by there being no operation that could drop one — rather than by every adapter remembering not to. A test checks the property; the absent operation is what survives an adapter written by someone who never read the test. Related: in-flight state is deliberately *not* persisted, because a crash between marking and the result arriving would leave an entry that is neither pending nor resolved. Idempotent replay against a server that already dedupes is safer than a client guessing what the network did. | This slice (CS-8); Plan §R1; D-009 | 23 Sep 2026 |

| D-045 | **Conflict classes never make the client skip a change the server applied.** The obvious reading of "append-only never overwrites" is that the client drops a second version — and that is wrong. The scope digest is computed over the rows a client holds (`docs/spec.md` §5), so skipping a change the server applied puts the two sides permanently out of step: divergence reported on every pull, a re-bootstrap, the same change again, skipped again, forever. A conflict policy that manufactures the exact failure the divergence detector exists to catch is a bug with a rationale. The server therefore stays the source of truth for row content in every class; what the classes govern is which commands may be **queued**, whether a losing edit is **recovered**, and whether a contract the server broke is **reported**. An append-only overwrite is refused as a whole batch, which is safe precisely because refusal writes nothing. | This slice (CS-9); [Spec](spec.md) §5, §6 | 23 Sep 2026 |

| D-046 | **`lww_winner` takes no timestamp argument.** `docs/spec.md` §6 makes `client_ts` a tiebreaker hint only, *"because device clocks lie"* — a phone three days fast would otherwise win every conflict it entered, and the user whose clock is correct would silently lose their work to whoever had the most broken device. Rather than documenting that `client_ts` must not decide, the comparison function cannot see it: it takes two `RowVersion`s and nothing else. A function that cannot read the clock cannot be corrupted by it, which is a stronger guarantee than a comment asking the reader not to. | This slice (CS-9); [Spec](spec.md) §6 | 23 Sep 2026 |

| D-047 | **The registry maps command names to entities, and an unregistered command is refused.** A `Command` carries a domain operation name, not an entity, so "no command may target a server-authoritative entity" is unenforceable without the host declaring which entity each command writes. Unregistered commands are refused rather than permitted: defaulting to allow would mean the protection applies only to entities someone remembered to register, which is the convention it was built to replace. An engine with an empty registry therefore accepts no commands at all — a host that forgets gets a loud refusal on its first write instead of a silently absent guarantee. | This slice (CS-9); Design §6 | 23 Sep 2026 |

| D-048 | **Proptest case counts are tiered by job, and every suite reads `PROPTEST_CASES`.** Pull requests run the count these suites have always run; nightly runs sixteen times that; Miri runs four cases. The tiers exist because the jobs ask different questions — a PR asks whether a change breaks something known, with a person waiting; nightly asks whether anything here has never been thought of, with all night. **No tier is lower than what CI ran before this slice**; weakening a gate is the one forbidden move (CLAUDE.md §3), and a nightly job running less than CI would be that in disguise. This required a change: every suite hardcoded `cases: 256`, which silently overrides `ProptestConfig::default()`'s own reading of the environment, so setting the variable had no effect whatsoever. `common::config(n)` now reads it. | This slice (CS-10); Playbook §5 | 23 Sep 2026 |

| D-049 | **`-Zmiri-disable-isolation` is required for the Miri gate, and is not a weakened gate.** `proptest` calls `std::env::current_dir()` to locate its failure-persistence file; Miri's sandbox refuses `getcwd` and the run aborts with `unsupported operation` before testing anything. The flag relaxes Miri's *sandbox*, not its undefined-behaviour checking, which is the only part this gate is buying. Without it the job does not run at all — and an aborted gate reads a great deal like a passing one, which is the failure mode this register exists to prevent. Miri also needs nightly, which `rust-toolchain.toml` deliberately does not pin: D-021 pins the toolchain the code is *built* with, and Miri is a checker rather than a build target, so every Miri invocation says `+nightly` explicitly. | This slice (CS-10); D-021 | 23 Sep 2026 |

| D-050 | **Property tests are skipped under Miri on pull requests, and run under it nightly.** Not a case-count problem: the cost is in *building* proptest's regex-backed string strategies, so turning `PROPTEST_CASES` down to 1 barely helps and the suites still dominated the job by an order of magnitude. Every proptest-generated test therefore carries `#[cfg_attr(miri, ignore)]`, and the nightly job runs them with `--include-ignored` at one case. What Miri buys this project is soundness of the **dependencies** — `serde_json`, `twox-hash`, `blake3` — since `credsync-core` and `credsync-protocol` are both `#![forbid(unsafe_code)]` and cannot express undefined behaviour themselves. The ~130 unit tests that still run under Miri walk every one of those code paths; more inputs through the same unsafe code finds no new unsoundness, it finds logic bugs, which is what the native run at 256 cases and the nightly run at 4096 are for. **No gate is weakened**: every property test runs in full on every pull request under `cargo test`. | This slice (CS-10); D-048 | 23 Sep 2026 |

| D-051 | **The simulator's generator is written by hand, not taken from a crate.** A generator from the ecosystem could change its output between versions — a bug fix, a different stream-selection rule, a faster mixing function — and every seed recorded in every bug issue would silently begin replaying a *different* run. The seeds in this tracker are meant to be good indefinitely, so PCG-XSH-RR 64/32 is pinned in `credsync-sim/src/rng.rs` where a change to it is a visible diff rather than a dependency bump. It also keeps `rand` and `getrandom` out of the workspace entirely, which the sans-IO source check watches for. Draw counts are held constant across every branch of a fault decision for the same reason: a decision whose cost depended on its outcome would shift every later decision. | This slice (CS-11); Design §7.1; D-038 | 23 Sep 2026 |

| D-052 | **The simulator models a server rather than driving `credsync-server`.** The real server does not exist until M3, and the client's slices cannot wait for it — a client tested only against itself is tested against its own assumptions. `credsync-sim/src/server.rs` implements what `docs/spec.md` requires of a conforming server and nothing else: `seq` as one `bigserial` shared across scopes so a scope's entries stay sparse (D-040), dedupe by command id recording the outcome, a mutated replay refused rather than deduped, and server-assigned `row_version` deciding last-write-wins. When the real server lands, the conformance suite is what proves the two agree. The **client** under test is the real `credsync_core::Engine`, unmodified. | This slice (CS-11); Design §7.1 | 23 Sep 2026 |

| D-053 | **The seed batch is not a CI gate until CS-12 gives it invariants.** A 1,000-seed batch takes 22 minutes and, today, asserts nothing about the engine: the harness checks its own determinism, fault coverage and time compression, but the invariants that would make a seed *fail* — convergence, durability, no-loss — arrive at CS-12 (#13). Wiring it in now would buy 22 minutes of CI time for a check that cannot go red for a reason anyone cares about, and a gate that never fails teaches people to ignore gates. `CLAUDE.md` §5 already asks for the batch before a pull request; it becomes a required check when it can report something. | This slice (CS-11); Playbook §5 | 23 Sep 2026 |

| D-054 | **Convergence is checked at quiescence; every other invariant is checked continuously.** Design §7.1 requires continuous checking, because a bug that self-corrects before a run ends is still a bug — it corrupted state and a later event happened to paper over it. Convergence is the one exception, and deliberately: a device mid-batch is *supposed* to disagree with the server, so checking it continuously would make the invariant fire on entirely normal operation, which is how an invariant gets switched off. `World::settle` therefore turns the faults off, stops all new writes, and gives every device time to finish before comparing. Turning the faults off is not enough on its own — devices that kept authoring and a server that kept taking external writes would outrun the devices forever and every run would look divergent. | This slice (CS-12); Design §7.1 | 23 Sep 2026 |

| D-055 | **The simulator's kill fault restarts the device.** `storage-committed-then-killed` first modelled a process kill by returning an error and letting the engine carry on, which is a different fault entirely: a storage layer that lies about having committed. The engine then ran with in-memory state describing a database that had moved on without it, and its digest regressed permanently. Caught by the convergence invariant on its first run — three devices, identical cursors, identical row counts, three different digests. A kill destroys the process, so the fault now restarts the device, which reloads from storage and replays its outbox against a server that dedupes. The *other* fault it accidentally modelled turned out to be worth defending against on its own merits and is filed as #55. | This slice (CS-12); Design §7.1 | 23 Sep 2026 |

| D-056 | **Convergence at quiescence is a weak ordering check; applied-state replaces it.** The CS-13 drill planted an ordering bug — apply a batch's changes in reverse — that the unit suite caught instantly and the simulator missed across **thirty seeds**. The reason is structural: a row corrupted mid-run is silently repaired by the next change to touch it, so only a corruption in the *final tail batch* survives to be compared, and the tail is usually a single change. `check_applied_state` checks every step instead: every row a device holds must be at the version its cursor implies, which the simulated server can answer exactly. With it the same bug is caught on every seed within hours of simulated time. Convergence is kept, because it catches whole-scope disagreement that per-row checks would miss, but it is no longer the primary ordering check. | This slice (CS-13); Design §7.1, §11 | 23 Sep 2026 |

| D-057 | **The simulated server must be allowed to break the protocol.** It built batches from its own log, where `seq` increases by construction, and pushes from the outbox, which never names a command twice — so the client's ordering and dedupe checks were never exercised by anything at all. Two planted bugs were therefore invisible: loosening the strict-ordering rule changed nothing observable, and dropping the resolve-once check changed nothing observable. The `protocol_violation` fault sends responses that decode perfectly and are still wrong: a repeated change, a repeated result. It is distinct from `malformed_bytes`, which produces bytes that do not decode at all — a buggy or hostile peer is not the same fault class as a corrupted one, and only the first exercises the validation the client actually has. | This slice (CS-13); Design §7.1 | 23 Sep 2026 |

| D-058 | **The server's integration tests require a real Postgres and fail loudly without one.** Not skipped, not mocked. The parts of CS-14 worth testing are exactly the parts a mock would invent: `bigserial` allocating `seq` under concurrent inserts, check constraints refusing a malformed row, `WHERE scope =` isolating a tenant, and `ORDER BY seq` meaning what it says — a mock agrees with whatever the code expected. Skipping when `CREDSYNC_TEST_DATABASE_URL` is unset would be worse still: the suite goes green on a machine that never ran it and nobody notices until the day it matters. `scripts/test-postgres.sh` makes satisfying the requirement one command, so the rule does not quietly become something people route around; CI uses a service container. | This slice (CS-14); Playbook §5 | 24 Sep 2026 |

| D-059 | **Test scopes are unique per test *and* per run.** Both halves were learned by getting them wrong. Per test, because `cargo test` runs these concurrently against one database — the first draft truncated the tables between tests instead, and six of eleven failed in ways that looked like ordering bugs. Per run, because the local test cluster is long-lived rather than a fresh container, so a second `cargo test` saw the first run's rows and every count assertion doubled. The scope carries the test name and the process id. This is also closer to production than a clean database would be: one shared `bigserial` log holding many tenants' changes interleaved, which means every test exercises the scope isolation rather than only the one that names it. | This slice (CS-14); [Spec](spec.md) §8 | 24 Sep 2026 |

| D-060 | **The batch checksum covers the changes, not the whole batch.** `docs/spec.md` §5 says a batch carries a checksum "over its canonical encoding", which is self-referential while `checksum` is itself a field of the batch — a checksum cannot cover the bytes it is part of. Covering the `changes` array is the reading that means something: those are the bytes corruption would damage, and the ones a client re-fetches when it detects it. Noted at CS-5 as a spec gap and settled here, where the server first has to compute one. | This slice (CS-14); [Spec](spec.md) §5 | 24 Sep 2026 |

| D-063 | **Pull withholds changes whose inserting transaction may still be in flight.** `seq` is a `bigserial`, which allocates when the `INSERT` runs — but a row becomes *visible* when its transaction commits, and those orders differ. Demonstrated against Postgres 14: transaction A takes `seq 1` and stays open, B takes `seq 2` and commits, and a reader sees only `seq 2`. A client would advance its cursor past `1` and **never be given change 1** — silent loss, invisible to every ordering check because the batch it received was perfectly ordered. The query therefore returns only rows whose inserting transaction finished before the oldest currently-running one began; a row that might still be in flight is withheld rather than reordered, and arrives on the next pull. The cost is latency bounded by the slowest concurrent writer's transaction; the alternative is losing writes. **Found by review, not by the simulator** — the simulated server is single-threaded, so no two writes are ever in flight at once, which is a real gap in what the rig can see. | This slice (CS-14); [Spec](spec.md) §4 | 24 Sep 2026 |
